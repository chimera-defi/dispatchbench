# model-routing-bench

Which model and reasoning effort should a coding task be routed to? This repo measures six Claude Code and Codex CLI configs on 12 Python problems written after the models' training cutoff, plus 4 small repo tasks. For each config it records where pass rate drops, and what a passing answer costs in dollars and seconds.

It was run once, on 2026-10-22, for $2.06 of measured Claude spend and $2.42 of Codex usage priced at list rates, including a harder rung added afterwards. Every number below is regenerated by `make report` from the cached calls, with no model calls.

## Result

| config | pass@1 | 95% CI | median s | p90 s | $ per pass | $ kind |
|---|---|---|---|---|---|---|
| haiku-low | 95% (57/60) | 85–100% | 10.0 | 16.0 | 0.00112 | measured |
| haiku-medium | 98% (59/60) | 93–100% | 13.0 | 26.8 | 0.00149 | measured |
| sonnet-medium | 100% (60/60) | ≥78% | 10.1 | 18.1 | 0.01244 | measured |
| luna-low | 77% (46/60) | 53–95% | 7.2 | 11.6 | 0.00090 | proxy |
| luna-medium | 78% (47/60) | 57–97% | 8.2 | 11.8 | 0.00089 | proxy |
| sol61-medium | 97% (58/60) | 87–100% | 22.6 | 36.2 | 0.01499 | proxy |
| luna-high (exploratory) | 92% (55/60) | 82–100% | 12.2 | 22.9 | 0.00105 | proxy |
| luna-low-bare (exploratory) | 73% (44/60) | 52–92% | 6.8 | 11.1 | 0.00080 | proxy |

Function track: 12 problems × 5 attempts per config. "$ per pass" is total spend divided by passing attempts. Claude dollars are the CLI's reported `total_cost_usd`; Codex dollars are token counts times list price ([results/prices.json](results/prices.json)). The two exploratory rows were added after the main run: luna-high is luna at high effort on all 12 problems, and luna-low-bare is luna-low with the Codex harness stripped to its smallest prompt (see below).

1. **"Low effort" is not the same budget on both CLIs, and that explains most of luna's gap.** At low and medium effort luna emits a mean of 0 and 7 reasoning tokens per call; haiku-low emits about 1,030. At those settings luna passes 77–78%, and haiku-low passes 95% (paired difference +18.3 pts, CI +1.7 to +38.3). At high effort luna emits about 530 reasoning tokens and passes 92% (55/60), 3.3 pts below haiku-low (CI −13.3 to +6.7). Its cost per pass, $0.00105, is close to haiku-low's $0.00112, and its median latency is 12.2 s against 10.0 s.
2. **Luna's misses at low and medium effort cluster on three problems.** Together they pass 2/10 attempts on p04 (L2), 6/10 on p11 (L6) and 0/10 on p12 (L6). The pre-registered escalation re-ran those three at high effort: 13/15 against luna-medium's 3/15. The three were chosen because luna failed them, so that ratio overstates the general gain; the full-ladder luna-high run above is the unbiased version (+13.3 pts against luna-medium, CI −5.0 to +35.0).
3. **Stripping the Codex harness cuts input tokens by 59% but does not make luna as accurate as Haiku.** Turning off tools, features, environment context and the stock system prompt takes luna's minimum input from 14,389 to 5,845 tokens. On the three pilot problems, stripped luna and haiku-low both pass 9/9, at $0.00030 and $0.00028 per call. On the full 12-problem ladder, stripped luna passes 73% against haiku-low's 95%: −21.7 pts, CI −43.3 to 0.0, so the interval's upper end touches zero. Stripping did not change luna's own accuracy (−3.3 pts against stock luna-low, CI −20 to +13). Its cost per pass, $0.00080, is below Haiku's measured $0.00112 only because of Codex's prompt cache: with no input served from cache it would be $0.00120, 7% above Haiku.
4. **The agentic tasks did not separate the configs.** All four configs passed every hidden test in 12 of 12 runs. What differs is cost per run: luna-low $0.0040, haiku-low $0.0051, sonnet-medium $0.054, sol61-medium $0.075, a 19× spread for the same outcome. sol61-medium also took 89 s at the median against 28 s for the other three. Part of the Codex cost and time is the host's `AGENTS.md`, which Codex loads and which told the agent to run extra search and delegation checks: 50 of sol61's 97 shell commands and 26 of luna's 62 came from it. The Codex agentic numbers are therefore upper bounds for a clean install.

A routing rule these numbers support: send to haiku-low by default. luna-high is a near-equal alternative on accuracy and cost, slightly slower, and its dollars are a proxy. Do not route to luna at low or medium effort for anything past L1: at those settings it barely reasons. sonnet-medium is the one config that never failed (75/75 including L7), at about 11× haiku-low's price per pass on L1–L6.

### Codex harness floor

Each trim level adds Codex CLI 0.163.0 config knobs to the one before. The probe is one call per level on a trivial problem, at low effort.

| model | stock harness | + no project docs | + no env/permission context | + tool features off | + one-line system prompt | + shell tools off |
|---|---|---|---|---|---|---|
| gpt-6-luna | 14,389 | 14,389 | 14,210 | 9,930 | 6,485 | 5,845 |
| gpt-5.6-terra | 14,201 | 14,197 | 14,020 | 9,469 | 5,928 | 5,288 |

About 1.3k of the remaining tokens are the user-level `~/.codex/AGENTS.md` on the host that ran this, which no flag turns off. A clean install would sit lower; I did not measure it, because doing so meant copying the CLI's login file into a temporary home. terra at the smallest prompt costs $0.0080 per call on the pilot problems, about 28× haiku-low, so it was not run on the full ladder.

## Harder rung (L7), added after the main run

Three more problems, written and checked before any model saw them (PLAN.md, deviation 16), each harder than p12: a cellular automaton on a ring run for up to 10^18 steps (p13), exact expected turns on a board game with bounce-back and chained jumps (p14), and paint/erase operations on 10^9 cells (p15). Four configs, 5 attempts each. These rows are kept apart from L1–L6 and change no number above.

| config | passed | p13 | p14 | p15 | median s | mean reasoning tokens | $ per pass | $ kind |
|---|---|---|---|---|---|---|---|---|
| luna-high | 15/15 | 5/5 | 5/5 | 5/5 | 24.0 | 1,569 | 0.0015 | proxy |
| sol61-medium | 15/15 | 5/5 | 5/5 | 5/5 | 35.2 | 482 | 0.0170 | proxy |
| sonnet-medium | 15/15 | 5/5 | 5/5 | 5/5 | 15.0 | 806 | 0.0180 | measured |
| haiku-low | 12/15 | 5/5 | 5/5 | 2/5 | 16.5 | 2,506 | 0.0023 | measured |

- **Only haiku-low failed, and only on speed.** All three misses are timeouts on the same p15 case: 50,000 single cells painted with a high colour, then 50,000 paints across the whole strip. All three failing solutions keep a sorted list of coloured intervals and visit every interval a paint covers, which is quadratic on that case; both passing attempts used a segment tree with lazy updates. None of haiku-low's answers was wrong.
- **The other three did not separate.** With 3 problems, 15/15 only bounds the pass rate at ≥37% (one-sided 95%), so this says L7 is still not hard enough for them, not that they are equally strong. What does separate them is price and time: luna-high costs $0.0015 per pass (proxy) against $0.017–0.018 for sol61-medium and sonnet-medium, and sonnet-medium is the fastest at 15 s.
- Both effort-adaptive configs spent more reasoning on L7 than on L1–L6: haiku-low 2.4× (1,027 → 2,506 tokens), luna-high 3.0× (526 → 1,569).

| p12 L6 | 4 (1c) | 5 | 5 | **0** (4c 1w) | **0** (4c 1w) | 3 (2c) | 3 (2c) | **0** (4c 1w) |
| p15 L7 | **2** (3t) | – | 5 | – | – | 5 | 5 | – |

- **sonnet-medium never failed**: 75/75 across L1–L7.
- **p12 (a spreadsheet evaluator) is where most configs break, and they break by crashing.** Of luna-low, luna-medium and stripped luna's 15 attempts, 9 raise a parse error on one of the statement's own worked examples and 3 hit Python's recursion limit on a long chain of cell references; haiku-low's one miss is also the recursion limit.
- **luna at low and medium effort fails p04 at L2**, a sliding-window count, and 8 of its 9 wrong answers are on the statement's own first worked example, `taller_within([5, 1, 4, 4, 9], 2)`. luna-high and every Claude config pass it 5/5, which is why the rung order is called a prior, not a measurement.
- **haiku-low fails by being slow, not wrong**: 5 timeouts (p09, p15) and 1 crash over 75 attempts, no wrong answers. haiku-medium's one miss is a wrong answer on p05.

## Method

The design was pre-registered in [PLAN.md](PLAN.md) and committed before the first model call. Changes made after that are listed at the end of that file, as numbered deviations.

**Configs.** Six base configs, each a CLI, a model and a reasoning effort:

| config | CLI | model | effort |
|---|---|---|---|
| haiku-low, haiku-medium | Claude Code | claude-haiku-5-5 | low, medium |
| sonnet-medium | Claude Code | claude-sonnet-5-5 | medium |
| luna-low, luna-medium | Codex CLI | gpt-6-luna | low, medium |
| sol61-medium | Codex CLI | gpt-6.1-sol | medium |

**Function track.** 12 problems on 6 rungs (L1–L6), two per rung. Each prompt asks for one Python function. Tools are off: Claude runs with `--tools ""`; Codex runs in a read-only sandbox and is told not to use tools. Every problem ships with:

- an efficient reference;
- an independently written brute force that must agree with the reference on 2,000 random small inputs;
- at least two planted wrong solutions (greedy, off-by-one, float rounding, too slow, a missed rule) that the checker must reject.

`make selftest` checks all three. Candidates run in a separate `python3 -I` process with a 2 GB memory cap. Large cases get max(2 s, 10 × the reference's time). Grading happens after generation, one problem at a time, so parallel model calls cannot cause false timeouts. The L6 problems were written after a calibration run showed three configs passing all of L1–L5 (PLAN.md, deviation 5).

**Agentic track.** 4 small repo tasks: add a feature, fix four bugs, add config interpolation, add a retry queue. Each has visible tests plus hidden tests that are copied in only after the agent exits. Both CLIs get shell and file-edit tools, and no user settings or MCP servers. A run passes when every hidden test passes. The harness also records whether the agent edited the original tests (none did) and whether it wrote the regression test the task asked for.

**Escalation.** Pre-registered rule: if a model's highest base effort passes 2/5 or fewer on a problem, the next effort level runs 5 attempts on that problem only. It fired once, for luna. Because the subset is picked by failure, the escalation table reports counts and no interval.

**Statistics.**

- pass@1 is the fraction of single attempts that pass, with no retries and no picking of the best answer.
- Intervals are 95% hierarchical bootstrap intervals, 10,000 resamples. Each resample draws problems, then attempts within each problem, so five attempts at one problem do not count as five independent data points ([Miller 2024](https://arxiv.org/abs/2411.00640)).
- When every attempt passes, the bootstrap interval collapses to 100–100%. The table then shows the one-sided 95% lower bound 0.05^(1/m), with m the number of problems (12, giving ≥78%) or tasks (4, giving ≥47%), not attempts, so that repeats of one problem are not counted as independent.
- Differences between configs are paired on the same problems.
- The breaking point of a config is the lowest rung where it passes 40% or less.

**Cost.** Claude dollars are the CLI's measured `total_cost_usd`. Codex dollars are a proxy: input tokens not served from cache, cached input tokens and output tokens, each at its list price from the model's page on developers.openai.com (URLs and access date in [results/prices.json](results/prices.json)). Read them as what these tokens would cost on the API, not as an invoice.

**Reproducibility.** Every model call is cached under `cache/`, keyed by the SHA-256 of the config, CLI version, harness flags, prompt, problem and attempt number. Every grade is cached by problem hash and code hash.

```bash
make report
```

rebuilds every table, chart and number in this README from the cache. It makes no model calls and needs neither CLI installed. `make run`, `make hard` and `make agentic` call models only for keys that are not cached yet.

## Limitations

- **Small sample.** 12 problems and 4 agentic tasks, with 5 and 3 attempts. The intervals are wide; read them before the point estimates.
- **The breaking point is unstable at this size.** With 10 attempts per rung, two attempts move it. Stripped luna breaks at L2 (4/10) and stock luna at L6, yet stripped luna then scores 10/10 on L3. The rung order is my prior about difficulty, not a measurement, and the per-problem chart shows where it was wrong (for luna, p04 at L2 is harder than every problem except p12).
- **The agentic track hit a ceiling.** All 48 runs passed. It shows cost and latency differences, not capability differences.
- **Codex cost is a proxy**, and it depends on the provider's prompt cache. Identical prompts got between 0 and 6.1k cached tokens (stripped luna on p06), which moves a Codex call's cost by up to 2×. The stripped-luna row gives a no-cache bound for that reason. Claude cost is measured, but it is the CLI's own accounting.
- **Harnesses are matched, not identical.** Codex cannot turn tools off on the function track; it gets a read-only sandbox and an instruction. Codex also injects the host's user-level `AGENTS.md` (about 1.3k tokens), so every Codex input count includes tokens a clean install would not have. Claude Code keeps its own default system prompt.
- **Latency is wall-clock through the CLI** on one host with up to 4 calls in flight. It includes CLI start-up and network time, and is not comparable to API time-to-first-token. The exploratory stripped-luna run used one lane at a different time of day, so its latency is not a clean comparison with luna-low.
- **The cache key leaves out a few inputs.** The effort and model literals inside the trim probe are not hashed. The one-line system prompt and the grader's source are pinned by SHA-256 instead: the runners and the grader refuse to run if either file changes while cached results exist.
- **The agentic runs are not sandboxed alike.** Claude Code ran with permission prompts bypassed and no sandbox; Codex ran in its workspace-write sandbox. The hidden tests run the agent's code with pytest outside the grader's sandbox. All of it ran in throwaway directories on one host.
- **L7 was not pre-registered either**, and has only 3 problems; it ran on four of the eight configs.
- **luna-high on the full ladder was not pre-registered.** It was added because the reasoning-token gap above made the low/medium comparison unfair to luna. Treat its row as exploratory.
- `make selftest` takes about 12 minutes; `make report` takes seconds.
- **One run in time.** Hosted models change. CLI versions and run dates are in [results/manifest.json](results/manifest.json); a later re-run may differ.

## Prior work this borrows from

- [LiveCodeBench](https://livecodebench.github.io/) ([Jain et al. 2024](https://arxiv.org/abs/2403.07974)): problems written after the models' training cutoff, to limit contamination.
- [SWE-bench](https://www.swebench.com/) ([Jimenez et al. 2023](https://arxiv.org/abs/2310.06770)) and [SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/): grade repo tasks with tests the agent never sees, and check the tests themselves. Here that check is the brute-force agreement and the planted-bug rejection.
- [Adding Error Bars to Evals](https://arxiv.org/abs/2411.00640) (Miller 2024): clustered resampling when one question has several attempts, and paired comparisons between models.
- [METR, measuring long tasks](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/): describe a model by where its success rate drops, not by one average.
- [Aider leaderboards](https://aider.chat/docs/leaderboards/) and [Artificial Analysis](https://artificialanalysis.ai/): report cost and speed next to accuracy.
- [Hamel Husain on evals](https://hamel.dev/blog/posts/evals/): read the failures. The per-problem chart and the outcome counts are here for that reason.

## Layout

```
bench/            problems, prompts, runners, sandboxed grader
  problems/       15 problems (12 on L1-L6, 3 on L7): statement, reference, brute force, planted bugs
  agentic/        4 repo tasks (visible tests, hidden tests, reference solution) and their runner
  pilot/          the earlier pilot's prompts and problems, reused by the trim probe
  run.py          function-track runner (cache-first, 4 lanes max, $8 Claude cap)
  escalate.py     pre-registered escalation step
  trim_probe.py   Codex harness floor probe (exploratory)
analysis/         statistics, summary tables, SVG charts (standard library only)
cache/            cached model calls and grades; the source of every number
results/          graded rows (jsonl), prices, manifest, summary, report
PLAN.md           pre-registration and deviations
```
