@readme Which model and reasoning effort should a coding task be routed to? This repo measures {{n_configs}} Claude Code and Codex CLI configs on {{n_problems}} Python problems written after the models' training cutoff, plus {{n_tasks}} small repo tasks. For each config it records where pass rate drops, and what a passing answer costs in dollars and seconds.

The main run was on 2026-10-22: {{claude_usd}} of Claude CLI-reported spend (function + agentic only; auxiliary runs and pilot excluded) and {{codex_old_usd}} of Codex usage priced at list rates. Five more Codex configs were added on {{new_date}} for {{codex_new_usd}} (finding 5), and the fast-mode and xhigh runs for {{fx_usd}}. Every number on this page is regenerated by `make report` from the cached calls, with no model calls, and `make audit` fails if any of them disagrees with the data.

> **Routing rule these numbers support:** while Codex has quota, build with a Codex config that never failed, sol61-high (finding 5): {{claude_zero}} on the Claude bill, at the cost of Codex usage and time; haiku-low repairs only when a check fails. Claude only (Codex out): haiku-low ({{haiku_low_pass}}, {{haiku_low_upp}} per pass) misses only by being slow or crashing; send a failed check, or a task where a miss is costly, to haiku-medium: {{haiku_medium_k}} on all problems, {{haiku_medium_upp}} per pass, and no miss on luna-low's hardest problems (its main-run attempts there), where it is {{hm_vs_pipe_x}} cheaper than the best luna→Haiku pipeline (Appendix A). Do not rely on luna at low or medium effort: it already fails an L2 problem, and at those settings it barely reasons. Where a miss must not happen, haiku-high is the cheapest config that never failed: {{hh_k}} on L1–L6, {{hh_hk}} on L7 and {{ag_hh_k}} repo-task runs, at {{hh_upp}} per pass (finding 7, exploratory). sonnet-medium never failed either ({{sm_all}} including L7), at about {{sm_vs_hl_x}} haiku-low's price per pass.

## Can luna run on fewer tokens?

Codex has no single switch like Claude's `--tools ""`. Turning off its tool features, shell tools, environment context and stock system prompt, six config knobs in all, cuts luna-low's mean input from {{luna_low_in}} to {{luna_low_bare_in}} tokens per call, {{in_cut}} less. No measurable change in accuracy: the stripped config passes {{luna_low_bare_pass}} against stock luna-low's {{luna_low_pass}} ({{lb_vs_ll}} pts, CI {{lb_vs_ll_ci}}, which rules out neither a gain nor a loss). Its proxy cost per pass falls from {{luna_low_upp}} to {{luna_low_bare_upp}}.

Even stripped, luna's input is larger than Claude's with tools off: haiku-low's mean is {{haiku_low_in}}. ## What it found

1. **"Low effort" is not the same budget on both CLIs, and on the point estimates that explains most of luna's gap.** At low and medium effort luna emits a mean of {{luna_low_rsn}} and {{luna_medium_rsn}} reasoning tokens per call; haiku-low emits about {{haiku_low_rsn10}}. At those settings luna passes {{luna_low_pass}} and {{luna_medium_pass}}, and haiku-low passes {{haiku_low_pass}} (paired difference {{hl_vs_ll}} pts, CI {{hl_vs_ll_ci}}). At high effort luna emits about {{luna_high_rsn10}} reasoning tokens and passes {{luna_high_pass}} ({{luna_high_k}}), {{lh_below_hl}} pts below haiku-low (CI {{lh_vs_hl_ci}}). Its cost per pass, {{luna_high_upp}}, is close to haiku-low's {{haiku_low_upp}}, and its median latency is {{luna_high_med}} s against {{haiku_low_med}} s.
2. **Luna's misses at low and medium effort cluster on three problems.** Together they pass {{p04_luna}} attempts on p04 taller_within (L2), {{p11_luna}} on p11 best_average (L6) and {{p12_luna}} on p12 sheet (L6). The pre-registered escalation re-ran those three at high effort: {{esc_k}} against {{esc_vs}}'s {{esc_base}}. The three were chosen because luna failed them, so that ratio overstates the general gain; the full-ladder luna-high run is the unbiased version ({{lh_vs_lm}} pts against luna-medium, CI {{lh_vs_lm_ci}}).
3. **Stripping the Codex harness halves luna's input but does not make it as accurate as Haiku.** On the full ladder stripped luna passes {{luna_low_bare_pass}} against haiku-low's {{haiku_low_pass}}: {{lb_vs_hl}} pts, CI {{lb_vs_hl_ci}}, so the interval's upper end touches zero. Its cost per pass, {{luna_low_bare_upp}}, depends on Codex's prompt cache: with no input served from cache it would be {{lb_upp_nocache}}, {{lb_nocache_above}} above Haiku's measured {{haiku_low_upp}} (which includes Claude's own cache discount).
4. **The repo tasks did not separate the configs.** The four configs first run passed every hidden test, {{ag_k}} runs each (so did the two added later, finding 5). What differs is cost per run: luna-low {{ag_luna_low_usd}}, haiku-low {{ag_haiku_low_usd}}, sonnet-medium {{ag_sonnet_medium_usd}}, sol61-medium {{ag_sol61_medium_usd}}, a {{ag_spread}} spread for the same outcome. sol61-medium took {{ag_sol61_medium_med}} s; luna-low took {{ag_luna_low_med}} s. The two Claude configs took about {{ag_other_med}} s.

5. **Two later Codex configs never failed, and they move the cost to the Codex bill** (exploratory, added {{new_date}}). sol61-high (gpt-6.1-sol at high effort) and astra-medium (gpt-6-astra) passed every L1–L6 attempt ({{x_sol61_high_k}}, {{x_astra_medium_k}}), every L7 attempt ({{x_sol61_high_hk}}, {{x_astra_medium_hk}}) and all {{ag_n}} repo-task runs. On luna's hardest problems, with haiku-low repairing only when the statement's examples fail, they needed {{g_sol61_repairs}} and {{g_astra_repairs}} repairs ({{r_sol61_high_haiku_on_fail_k}}, {{r_astra_medium_haiku_on_fail_k}}), so their Claude cost there was {{g_sol61_cupp}} and {{g_astra_cupp}} per pass. By list price they are dear: {{x_sol61_high_upp}} and {{x_astra_medium_upp}} per pass on L1–L6, {{x_s61h_vs_sm}} and {{x_astra_vs_sm}} sonnet-medium's. astra-medium is faster ({{x_astra_medium_med}} s against {{x_sol61_high_med}} s on L1–L6, {{ag_astra_medium_med}} s against {{ag_sol61_high_med}} s on the repo tasks) and uses about {{x_astra_vs_s61h}} as much at list price; both are much slower than a Claude builder on the repo tasks (about {{ag_claude_med}} s for haiku-low and sonnet-medium).
6. **The other later Codex configs change nothing.** sol56-high (gpt-5.6-sol) never fails on L1–L6 but misses on L7 ({{x_sol56_high_hk}}) at {{x_sol56_vs_hm}} haiku-medium's price per pass. The older luna is worse and dearer: luna56-high passes {{x_luna56_high_hk}} on L7 against gpt-6 luna-high's {{x_base_luna_high_hk}}, and costs {{x_l56_vs_lh}} as much per pass on L1–L6 (gpt-5.6-luna lists at twice gpt-6-luna's input price and more than twice its output price). Findings 5 and 6 are exploratory: the configs were chosen after the main results were known, and Codex dollars are list-price proxies.
7. **Parity starts at haiku-high** (exploratory, added 2026-10-24). haiku-medium still misses: {{haiku_medium_k}} on L1–L6 and {{hm_l7_miss}} on L7 ({{hm_l7_k}}). haiku-high passed every attempt: {{hh_k}} on L1–L6, {{hh_hk}} on L7 and {{ag_hh_k}} repo-task runs. It costs {{hh_upp}} per pass on L1–L6 ({{hh_vs_hm}} haiku-medium's, from {{hh_out_x}} the output tokens) and {{hh_hupp}} on L7. That is {{hh_sm_x}} cheaper than sonnet-medium, {{hh_s61h_x}} cheaper than sol61-high and {{hh_astra_x}} cheaper than astra-medium on L1–L6 ({{hh_sm_hx}}, {{hh_s61h_hx}} and {{hh_astra_hx}} on L7; the Codex figures are list-price proxies). It ran after the main results were known, so read it as a strong lead, not a pre-registered result.

## Method

The design was pre-registered in [PLAN.md](PLAN.md) and committed before the first model call. Changes made after that are listed at the end of that file, as numbered deviations.

**Configs.** {{n_configs}} base configs, each a CLI, a model and a reasoning effort:

{{table:configs}}

**Function track.** {{n_problems}} problems on {{n_rungs}} rungs (L1–L6), {{per_rung}} per rung. Each prompt asks for one Python function. Tools are off: Claude runs with `--tools ""`; Codex runs in a read-only sandbox and is told not to use tools. Every problem ships with:

- an efficient reference;
- an independently written brute force that must agree with the reference on 2,000 random small inputs;
- at least two planted wrong solutions (greedy, off-by-one, float rounding, too slow, a missed rule) that the checker must reject.

`make selftest` checks all three. Candidates run in a separate `python3 -I` process with a 2 GB memory cap. Large cases get max(2 s, 10 × the reference's time). Grading happens after generation, one problem at a time, so parallel model calls cannot cause false timeouts. The L6 problems were written after a calibration run showed three configs passing all of L1–L5 (PLAN.md, deviation 5).

**Repo tasks.** {{n_tasks}} small repo tasks: add a feature, fix four bugs, add config interpolation, add a retry queue. Each has visible tests plus hidden tests that are copied in only after the agent exits. Both CLIs get shell and file-edit tools, and no user settings or MCP servers. A run passes when every hidden test passes. The harness also records whether the agent edited the original tests (none did) and whether it wrote the regression test the task asked for.

**Escalation.** Pre-registered rule: if a model's highest base effort passes 2/5 or fewer on a problem, the next effort level runs 5 attempts on that problem only. It fired once, for luna. Because the subset is picked by failure, the escalation table reports counts and no interval.

**Statistics.**

- pass@1 is the fraction of single attempts that pass, with no retries and no picking of the best answer.
- Intervals are 95% hierarchical bootstrap intervals, {{n_boot}} resamples. Each resample draws problems, then attempts within each problem, so five attempts at one problem do not count as five independent data points ([Miller 2024](https://arxiv.org/abs/2411.00640)).
- When every attempt passes, the bootstrap interval collapses to 100–100%. The table then shows the one-sided 95% lower bound 0.05^(1/m), with m the number of problems ({{n_problems}}, giving ≥{{bound_problems}}) or tasks ({{n_tasks}}, giving ≥{{bound_tasks}}), not attempts, so that repeats of one problem are not counted as independent.
- Differences between configs are paired on the same problems.
- The breaking point of a config is the lowest rung where it passes {{break_at}} or less.

**Cost.** Claude dollars are the CLI's measured `total_cost_usd`. Codex dollars are a proxy: input tokens not served from cache, cached input tokens and output tokens, each at its list price from the model's page on developers.openai.com (URLs and access date in [results/prices.json](results/prices.json)). Read them as what these tokens would cost on the API, not as an invoice.

**Reproducibility.** Appendix arms B1, B2, C, D and the original arm E, plus the pilot, kept graded rows only; their runners and raw calls were not kept, so those rows cannot be re-graded. Arms F and G and the function and trim tracks have cached completions under `cache/` and can be re-graded. Agentic runs before this harness change kept only verdicts, without full candidate patches, so those outputs cannot be re-graded from the cache. New agentic runs save the full candidate patch in `cache/agentic_patches/<key>.patch` before cleanup and include the grader version in their cache keys. Function grades are cached by problem hash and code hash. Ordinary agentic runs reuse legacy verdicts; `--regrade` explicitly allows new model calls under the current grader. Export retains one row per config, task and repeat, with the newest grader version taking precedence. The trusted pytest process still imports the candidate package, so candidate code executes inside the grader. Retained patches and `tests_tampered` checks are the mitigations that make changes inspectable.

```bash
make report
```

rebuilds every table, chart and number in this README and the page from the cache. It makes no model calls and needs neither CLI installed. `make audit` re-renders both and fails if the committed copies differ, if `results/summary.json` differs from what the rows give, or if the template holds a number that is not computed from data and not on its short reasoned list of constants. `make run`, `make hard` and `make agentic` call models only for keys that are not cached yet.

## Limitations

- **Small sample.** {{n_problems}} problems and {{n_tasks}} repo tasks, with {{repeats}} and {{agent_repeats}} attempts. The intervals are wide; read them before the point estimates.
- **The breaking point is unstable at this size.** With {{rung_attempts}} attempts per rung, two attempts move it. Stripped luna breaks at L2 ({{lb_l2}}) and stock luna at L6, yet stripped luna then scores {{lb_l3}} on L3. The rung order is the author's prior about difficulty, not a measurement, and the per-problem chart shows where it was wrong (for luna, p04 taller_within at L2 is harder than every problem except p12 sheet).
- **The repo tasks hit a ceiling.** All {{ag_runs}} runs passed. They show cost and latency differences, not capability differences.
- **Codex cost is a proxy**, and it depends on the provider's prompt cache. Identical prompts got between 0 and {{cache_max}} cached tokens (stripped luna on p06 calc), which moves a Codex call's cost by up to {{cache_swing}}. The stripped-luna figures give a no-cache bound for that reason. Claude cost is measured, but it is the CLI's own accounting.
- **Harnesses are matched, not identical.** Codex cannot turn tools off on the function track; it gets a read-only sandbox and an instruction. Codex also injects the host's user-level `AGENTS.md` (about {{host_agents_md}} tokens), so every function-track Codex input count includes tokens a clean install would not have. Repo-task rows were rerun with a clean Codex home; a clean rerun of {{isolation_calls_matched}} function calls passed {{isolation_passes_isolated}} versus {{isolation_passes_original}}, so those rows were kept. Claude Code keeps its own default system prompt.
- **Latency is wall-clock through the CLI** on one host with up to {{lanes}} calls in flight. It includes CLI start-up and network time, and is not comparable to API time-to-first-token. The exploratory stripped-luna run used one lane at a different time of day, so its latency is not a clean comparison with luna-low.
- **The cache key leaves out a few inputs.** The effort and model literals inside the trim probe are not hashed. The one-line system prompt and the grader's source are pinned by SHA-256 instead: the runners and the grader refuse to run if either file changes while cached results exist.
- **The repo-task runs are not sandboxed alike.** Claude Code ran with permission prompts bypassed and no sandbox; Codex ran in its workspace-write sandbox. The hidden tests run the agent's code with pytest outside the grader's sandbox. All of it ran in throwaway directories on one host.
- **L7 was not pre-registered either**, and has only three problems; it ran on only some of the configs (see the L7 table).
- **luna-high on the full ladder was not pre-registered.** It was added because the reasoning-token gap made the low/medium comparison unfair to luna. Treat its row as exploratory.
- **The quality columns are descriptive.** Growth exponents come from the fastest of three timings at each of four input sizes on a shared host, so small differences are noise; the threshold for "worse than reference" is in PLAN.md.
- `make selftest` takes about 12 minutes; `make report` takes seconds.
- **One run in time.** Hosted models change. CLI versions and run dates are in [results/manifest.json](results/manifest.json); a later re-run may differ.

## Appendix A: can refinements rescue luna-low? (exploratory, post hoc)

After the main run, several changes were tried on the {{n_rescue_problems}} problems {{rescue_rule}}, the rescue set (p03 ledger, p04 taller_within, p08 recur, p09 k_machine_schedule, p10 avoid_count, p11 best_average, p12 sheet), with 5 attempts each, n = {{rescue_n}} per row. The problems were picked because luna failed them, so these rows overstate any gain and carry no confidence intervals. The baselines are the main run's attempts on the same problems. Rows are in [results/appendix/luna_rescue.jsonl](results/appendix/luna_rescue.jsonl).

{{table:rescue}}

- **Raising effort is the only cheap fix.** Stripped luna-high passes {{r_luna_high_bare_k}} at {{r_luna_high_bare_upp}} per pass (proxy), next to haiku-low's {{r_haiku_low_k}} at {{r_haiku_low_upp}}. Medium effort does nothing ({{r_luna_medium_bare_k}}), which fits the reasoning-token counts above: luna barely reasons below high.
- **Prompting helps a little or hurts.** The "trace the examples first" nudge adds {{r_b1_gain}} passes; asking for a reasoning summary on top of it loses {{r_b2_loss}}.
- **Letting luna test its own code works but costs more than switching models.** Self-testing reaches {{r_luna_low_selftest_k}} at {{r_c_cost_x}} the baseline's cost per pass and {{r_c_time_x}} its latency, more than haiku-low for fewer passes.
- **A Haiku review of every answer fixes almost everything, but Haiku does the work.** In the original arm E run, luna-low's own answers passed {{r_e_luna}}; Haiku changed {{r_e_changed}} of them and accounted for {{r_e_haiku_share}} of the spend, reaching {{r_luna_low_haiku_low_repair_k}}. Rerun from committed code (arm G, reconstructed prompt) it reached {{r_luna_low_haiku_review_all_k}}. With luna-high building, the review reached {{r_luna_high_bare_haiku_review_all_k}} at {{r_luna_high_bare_haiku_review_all_upp}} per pass.
- **Repairing only when the statement's examples fail is cheap and fast, but the examples are a weak check.** They flagged {{g_hi_fixed}} luna-high answers and let {{g_hi_missed}} failing ones through ({{r_luna_high_bare_haiku_on_fail_k}}; a luna-high retry instead of Haiku: {{r_luna_high_bare_retry_on_fail_k}}). luna-low fails them more often, so its gate fired {{g_lo_fixed}} times and reached {{r_luna_low_haiku_on_fail_k}} in a median {{r_luna_low_haiku_on_fail_s}}, the fastest row.
- **Planning first (arm F) did not help luna-high:** {{r_haiku_low_plan_luna_high_bare_k}}, against {{r_luna_high_bare_k}} alone.

## What we borrowed from other benchmarks

Methods:

- [LiveCodeBench](https://livecodebench.github.io/) ([Jain et al. 2024](https://arxiv.org/abs/2403.07974)): date the problems against the models' training cutoff to limit contamination. Every problem here was written after that cutoff.
- [EvalPlus](https://evalplus.github.io/) ([Liu et al. 2023](https://arxiv.org/abs/2305.01210)): the examples in a problem statement are too weak to grade with. Here each answer is graded against a reference solution on generated inputs, the reference must agree with an independent brute force, and every planted wrong solution must fail before a problem is used.
- [SWE-bench](https://www.swebench.com/) ([Jimenez et al. 2023](https://arxiv.org/abs/2310.06770)) and [SWE-bench Verified](https://openai.com/index/introducing-swe-bench-verified/): grade repo tasks with tests the agent never sees, and check that those tests are fair. The repo tasks copy in hidden tests only after the agent exits, and each ships a reference solution.
- [Adding Error Bars to Evals](https://arxiv.org/abs/2411.00640) (Miller 2024): resample by problem, not by attempt, and compare models on the same problems.
- [METR, measuring long tasks](https://metr.org/blog/2025-03-19-measuring-ai-ability-to-complete-long-tasks/): describe a model by where its success rate drops, here the breaking-point rung, not by one average.

Presentation:

- [Aider leaderboards](https://aider.chat/docs/leaderboards/): one leaderboard row per model setting, with pass rate and dollar cost side by side and the exact command recorded. Here the CLI versions are in `results/manifest.json` and every flag is in `bench/run.py`. Every table on the page sorts by any column.
- [Artificial Analysis](https://artificialanalysis.ai/): plot accuracy, price and speed against each other and mark the configs no other beats. The Pareto and cost-vs-time charts and the page's two frontier scatters do this.
- [Hamel Husain on evals](https://hamel.dev/blog/posts/evals/): read the failures, not only the average. The per-problem chart, the failure table and the exported solutions in `results/solutions/` are there so a reader can check any cell.

What we did not borrow: scale. These benchmarks run hundreds of problems, and LiveCodeBench keeps adding new ones; this is one run on {{n_all_problems}} problems, so its intervals are wide.
